# 完成前先验证(Verification Before Completion)

## 概览

**核心原则:** 永远证据在先,断言在后。

**违反本规则的字面,就是违反本规则的精神。**

## 铁律(The Iron Law)

```
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
```

没有新鲜验证证据,禁止任何完成声明。

如果你在本条消息里没有跑过验证命令,你就不能声称它通过。

## 门禁函数(The Gate Function)

```
在声称任何状态、或表达任何满意之前(BEFORE):

1. 识别(IDENTIFY): 什么命令能证明这个声明?
2. 运行(RUN): 执行完整命令( fresh、完整)
3. 阅读(READ): 读完整个输出,检查退出码,数失败数
4. 核实(VERIFY): 输出确认这个声明吗?
   - 如果不: 带着证据陈述实际状态
   - 如果是: 带着(WITH)证据陈述声明
5. 只有此时(ONLY THEN): 才作出声明

跳过任何一步 = 撒谎,不是验证
```

## 常见失败(Common Failures)

| 声明 | 需要 | 不充分的证据 |
|-------|----------|----------------|
| 测试通过 | 测试命令输出: 0 失败 | 之前跑过一次、「应该能过」 |
| Linter 干净 | Linter 输出: 0 错误 | 只查了部分、外推 |
| 构建成功 | 构建命令: exit 0 | Linter 过了、日志看着还行 |
| Bug 已修 | 测原始症状: 通过 | 代码改了、假定修好了 |
| 回归测试有效 | 红-绿循环已验证 | 测试通过过一次 |
| 代理完成了 | VCS diff 显示变更 | 代理报告「成功」 |
| 需求已满足 | 逐条核对清单 | 测试通过 |

## 红旗——STOP(Red Flags)

- 使用「应该」「大概」「看起来」
- 验证之前表达满意(「太好了!」「完美!」「搞定!」等)
- 未经验证就要 commit/push/建 PR
- 轻信代理的成功报告
- 依赖部分验证
- 想着「就这一次」
- 累了,想赶紧收工
- **任何暗示成功、却没有跑过验证的措辞**

## 合理化借口预防(Rationalization Prevention)

| 借口 | 现实 |
|--------|---------|
| 「现在应该能用了」 | 去跑(RUN)验证 |
| 「我很有信心」 | 信心 ≠ 证据 |
| 「就这一次」 | 没有例外 |
| 「Linter 过了」 | Linter ≠ 编译器 |
| 「代理说成功了」 | 独立核实 |
| 「我累了」 | 疲惫 ≠ 借口 |
| 「部分检查就够了」 | 部分证明不了任何东西 |
| 「措辞不同所以规则不适用」 | 精神重于字面 |

## 关键模式(Key Patterns)

**测试:**
```
✅ [跑测试命令] [看到: 34/34 通过] "所有测试通过"
❌ "现在应该能过" / "看着是对的"
```

**回归测试(TDD 红-绿):**
```
✅ 写测试 → 跑(通过) →  revert 修复 → 跑(必须失败) → 恢复修复 → 跑(通过)
❌ "我写了一个回归测试"(未经红-绿验证)
```

**构建:**
```
✅ [跑构建] [看到: exit 0] "构建通过"
❌ "Linter 过了"(linter 不检查编译)
```

**需求:**
```
✅ 重读 plan → 建核对清单 → 逐条验证 → 报告缺口或完成
❌ "测试过了,本阶段完成"
```

**代理委派:**
```
✅ 代理报告成功 → 查 VCS diff → 核实变更 → 报告实际状态
❌ 轻信代理报告
```

## 何时应用(When To Apply)

**以下情况永远(ALWAYS)先验证:**
- 任何形式的成功/完成声明
- 任何满意的表达
- 任何关于工作状态的正面陈述
- 提交、建 PR、标记任务完成
- 移向下一个任务
- 委派给代理

**本规则适用于:**
- 原话
- 转述与同义表达
- 对成功的暗示
- 任何暗示完成/正确的沟通
