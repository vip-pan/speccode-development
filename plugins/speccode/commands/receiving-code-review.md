# 接收代码审查(Code Review Reception)

## 概览

代码审查需要技术评估,不是情绪表演。

**核心原则:** 实施之前先核实。假设之前先提问。技术正确性高于社交舒适。

## 知识库入口

1. 运行 `speccode.mjs read-knowledge --cwd . --index` 读 `_index.md`(恒读,便宜);`exists:false` → 静默跳过本节。
2. 判断本任务相关主题 → `speccode.mjs read-knowledge --cwd . --topic <名称>` 读对应 topic 文件;`exists:false` → 静默跳过该主题。
3. 读取失败或目录不存在 → 静默跳过,绝不阻断主流程(T0 兜底,永不报错)。

## 响应模式(The Response Pattern)

```
收到代码审查反馈时:

1. 读(READ): 完整读完反馈,不做反应
2. 理解(UNDERSTAND): 用自己的话复述需求(或提问)
3. 核实(VERIFY): 对照代码库现实检查
4. 评估(EVALUATE): 对「这个」代码库在技术上成立吗?
5. 回应(RESPOND): 技术性确认,或有理由的反驳
6. 实施(IMPLEMENT): 一次一项,每项都测
```

## 禁止的响应(Forbidden Responses)

**绝不(NEVER):**
- "You're absolutely right!"(你说得完全对!)(明确违反指令文件)
- "Great point!" / "Excellent feedback!"(表演式)
- "Let me implement that now"(在核实之前)

**而要(INSTEAD):**
- 复述技术需求
- 提澄清问题
- 若反馈有误,用技术理由反驳
- 直接开始干活(行动 > 言语)

## 处理不清楚的反馈

```
如果有任何一项不清楚:
  STOP - 先不要实施任何东西
  就不清楚的项请求澄清

为什么: 各项之间可能相互关联。理解一半 = 实施错误。
```

**示例:**
```
人类伙伴: "修 1-6"
你理解 1、2、3、6。对 4、5 不清楚。

❌ 错: 先实施 1、2、3、6,4、5 以后再问
✅ 对: "我理解第 1、2、3、6 项。继续之前需要对第 4、5 项的澄清。"
```

## 按来源分别处理(Source-Specific Handling)

### 来自你的人类伙伴
- **可信** - 理解之后实施
- 范围不清**仍然要问**
- **不要表演式认同**
- **直接进入行动**或技术性确认

### 来自外部审查者
```
实施之前(BEFORE):
  1. 检查: 对「这个」代码库在技术上正确吗?
  2. 检查: 会破坏既有功能吗?
  3. 检查: 当前实现存在的理由是什么?
  4. 检查: 在所有平台/版本上都成立吗?
  5. 检查: 审查者理解完整上下文吗?

如果建议看起来是错的:
  用技术理由反驳

如果不容易核实:
  明说: "没有 [X] 我无法核实这一点。我应该 [调查/提问/照旧实施] 吗?"

如果与人类伙伴先前的决定冲突:
  停下来,先与你的人类伙伴讨论
```

**人类伙伴的规则:** 「外部反馈——保持怀疑,但仔细核查」

## 对「专业」功能的 YAGNI 检查

```
如果审查者建议「正规实现一下」:
  在代码库里 grep 实际用法

  如果没有调用方: "这个端点没有被调用。删掉它(YAGNI)?"
  如果有调用方: 那就正规实现
```

**人类伙伴的规则:** 「你和审查者都向我汇报。如果我们不需要这个功能,就不要加。」

## 实施顺序(Implementation Order)

```
对多项反馈:
  1. 先(FIRST)澄清一切不清楚的
  2. 然后按此顺序实施:
     - 阻塞性问题(崩溃、安全)
     - 简单修复(笔误、import)
     - 复杂修复(重构、逻辑)
  3. 每项修复单独测试
  4. 验证没有回归
```

全部反馈处理完成(逐项实施、单独测试、无回归)后,触发 onCodeReviewCompleted 钩子:

```bash
echo '{"command":"receiving-code-review","feature_branch":"<F>","worktree_branch":"<W>"}' | speccode.mjs run-hook --cwd . --event onCodeReviewCompleted
```

输出 `hook.ok=false` 或含 `warning` 时打印警告(含事件名与错误摘要),MUST NOT 阻断主流程。

## 何时反驳(When To Push Back)

以下情况要反驳:
- 建议会破坏既有功能
- 审查者缺少完整上下文
- 违反 YAGNI(没人用的功能)
- 对这个技术栈在技术上不正确
- 存在遗留/兼容性原因
- 与人类伙伴的架构决定冲突

**如何反驳:**
- 用技术理由,不要带防御情绪
- 提具体问题
- 引用能工作的测试/代码
- 涉及架构时让人类伙伴参与

**如果你不习惯当面反驳:** 点出这种紧张感,然后把你看到的问题告诉你的伙伴。他们会欣赏你的诚实。

## 确认正确的反馈(Acknowledging Correct Feedback)

当反馈确实正确时:
```
✅ "已修。[改了什么的简短描述]"
✅ "好发现 - [具体问题]。已在 [位置] 修复。"
✅ [直接修掉,在代码里体现]

❌ "You're absolutely right!"
❌ "Great point!"
❌ "Thanks for catching that!"
❌ "Thanks for [任何东西]"
❌ 任何形式的感谢表达
```

**为什么不道谢:** 行动说话。修掉就是。代码本身就表明你听到了反馈。

**如果你发现自己正要打出 "Thanks":** 删掉它。改为陈述修复。

## 优雅地纠正自己的反驳(Gracefully Correcting Your Pushback)

如果你反驳过、而你错了:
```
✅ "你是对的 - 我查了 [X],它确实 [Y]。现在就实施。"
✅ "核实过了,你是正确的。我最初的理解错了,因为 [原因]。修复中。"

❌ 长篇道歉
❌ 为自己为什么反驳辩护
❌ 过度解释
```

陈述事实性的更正,然后继续。

## 常见错误(Common Mistakes)

| 错误 | 修法 |
|---------|-----|
| 表演式认同 | 陈述需求,或直接行动 |
| 盲目实施 | 先对照代码库核实 |
| 一批改完不测 | 一次一项,每项都测 |
| 默认审查者是对的 | 检查是否会破坏东西 |
| 回避反驳 | 技术正确性 > 舒适 |
| 部分实施 | 先澄清所有项 |
| 核实不了还硬上 | 说明限制,请示方向 |

## 真实示例(Real Examples)

**表演式认同(坏):**
```
审查者: "删掉遗留代码"
❌ "You're absolutely right! Let me remove that..."
```

**技术性核实(好):**
```
审查者: "删掉遗留代码"
✅ "查一下…… 构建目标是 10.15+,这个 API 需要 13+。向后兼容需要这段遗留代码。当前实现的 bundle ID 有误——是修它,还是放弃 13 之前的支持?"
```

**YAGNI(好):**
```
审查者: "正规实现指标追踪:数据库、日期过滤、CSV 导出"
✅ "grep 过代码库——没有任何东西调用这个端点。删掉它(YAGNI)?还是有我没看到的用法?"
```

**不清楚的项(好):**
```
人类伙伴: "修第 1-6 项"
你理解 1、2、3、6。对 4、5 不清楚。
✅ "理解 1、2、3、6。实施之前需要对第 4、5 项的澄清。"
```

## GitHub 评论串回复(GitHub Thread Replies)

回复 GitHub 上的行内审查评论时,在评论串里回复(`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`),不要发成顶层 PR 评论。
