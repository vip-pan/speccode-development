# 系统化调试(Systematic Debugging)

## 概览

**核心原则:** 永远先找根因,再尝试修复。修症状就是失败。

**违反本流程的字面,就是违反调试的精神。**

## 铁律(The Iron Law)

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

未经根因调查,禁止修复。

如果你还没完成第 1 阶段,你就不能提出修复。

## 何时使用

用于任何技术问题:
- 测试失败
- 生产环境 bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**以下情况尤其要用:**
- 时间紧迫(紧急情况让「猜」变得诱人)
- 「就一个小修复」看起来很明显
- 你已经试过多个修复
- 上一个修复没起作用
- 你不完全理解这个问题

**以下情况也不要跳过:**
- 问题看起来简单(简单 bug 也有根因)
- 你很急(匆忙保证返工)
- 经理要它立刻修好(系统化比乱撞更快)

## 四个阶段(The Four Phases)

你 MUST 完成每个阶段才能进入下一个。

### 第 1 阶段:根因调查(Root Cause Investigation)

**在尝试任何修复之前(BEFORE):**

1. **仔细读错误消息**
   - 不要跳过错误或警告
   - 它们常常就包含确切的解法
   - 完整读堆栈跟踪
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠地触发它吗?
   - 确切步骤是什么?
   - 每次都发生吗?
   - 如果不能复现 → 收集更多数据,不要猜

3. **检查近期变更**
   - 什么改动可能导致这个?
   - git diff、近期 commit
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件(CI → 构建 → 签名,API → 服务 → 数据库):**

   **提出修复之前(BEFORE),先加诊断埋点:**
   ```
   对每个组件边界:
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传递
     - 检查每一层的状态

   跑一次,收集能显示「断在哪一层」的证据
   然后分析证据,定位失效的组件
   然后调查那个具体组件
   ```

   **示例(多层系统):**
   ```bash
   # 第 1 层:Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第 2 层:构建脚本
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 第 3 层:签名脚本
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层:实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了:** 哪一层失败(secrets → workflow ✓,workflow → build ✗)

5. **追踪数据流**

   **当错误深在调用栈里:**

   完整的回溯追踪技术见 `${CLAUDE_PLUGIN_ROOT}/references/root-cause-tracing.md`。

   **速览版:**
   - 坏值从哪来?
   - 谁拿着坏值调用了这里?
   - 一路向上追,直到找到源头
   - 在源头修,不在症状处修

### 第 2 阶段:模式分析(Pattern Analysis)

**修复之前,先找到模式:**

1. **找能工作的例子**
   - 在同一代码库里找类似的、能工作的代码
   - 有什么相似的东西是好的?

2. **对照参考实现**
   - 如果是在实现某个模式,完整读完参考实现
   - 不要略读——读每一行
   - 应用之前先完全理解这个模式

3. **识别差异**
   - 能工作的和坏掉的之间有什么不同?
   - 列出每个差异,无论多小
   - 不要假设「那不可能是原因」

4. **理解依赖**
   - 这个组件还需要什么别的组件?
   - 什么设置、配置、环境?
   - 它做了什么假设?

### 第 3 阶段:假设与检验(Hypothesis and Testing)

**科学方法:**

1. **形成单一假设**
   - 说清楚:「我认为 X 是根因,因为 Y」
   - 写下来
   - 具体,不含糊

2. **最小化检验**
   - 做尽可能小的改动来检验假设
   - 一次只动一个变量
   - 不要一次修多个东西

3. **继续之前先验证**
   - 起作用了?是 → 第 4 阶段
   - 没起作用?形成新假设
   - 不要在上面叠加更多修复

4. **当你不知道时**
   - 说「我不懂 X」
   - 不要装懂
   - 求助
   - 做更多研究

### 第 4 阶段:实现(Implementation)

**修根因,不修症状:**

1. **创建失败测试用例**
   - 尽可能简单的复现
   - 可能的话写自动化测试
   - 没有测试框架就写一次性测试脚本
   - 修复之前 MUST 有它
   - 用 `/speccode:test-driven-development` 写合格的失败测试

2. **实施单一修复**
   - 针对已识别的根因
   - 一次一个改动
   - 不要「顺手」改进
   - 不要捆绑重构

3. **验证修复**
   - 测试现在通过了?
   - 没有其他测试被破坏?
   - 问题确实解决了?
   - 声称成功之前,用 `/speccode:verification-before-completion`

4. **如果修复没起作用**
   - STOP
   - 数一下:你已经试了几次修复?
   - 如果 < 3:回到第 1 阶段,带着新信息重新分析
   - **如果 ≥ 3:STOP,质疑架构(下面的第 5 条)**
   - 不要在未经架构讨论的情况下尝试第 4 次修复

5. **如果 3+ 次修复失败:质疑架构**

   **表明架构问题的模式:**
   - 每次修复都在不同地方暴露出新的共享状态/耦合/问题
   - 修复需要「大规模重构」才能实施
   - 每次修复都在别处制造新症状

   **STOP,质疑根本:**
   - 这个模式从根本上成立吗?
   - 我们是不是「纯粹靠惯性在坚持」?
   - 应该重构架构,还是继续修症状?

   **在尝试更多修复之前,与你的人类伙伴讨论**

   这不是一个失败的假设——这是一个错误的架构。

## 红旗——STOP,回到流程(Red Flags)

如果你发现自己在想:
- 「先快速修一下,之后再调查」
- 「改改 X 试试看行不行」
- 「多加几个改动,跑下测试」
- 「跳过测试,我手动验证」
- 「大概是 X,我把它修了」
- 「我不完全理解,但这样可能行」
- 「模式写的是 X,但我要换个方式改编」
- 「主要问题是:[未经调查直接列修复清单]」
- 在追踪数据流之前提出解法
- **「再试一次修复」(已经试过 2+ 次)**
- **每次修复都在不同地方暴露新问题**

**以上每一条都意味着:STOP。回到第 1 阶段。**

**如果 3+ 次修复失败:** 质疑架构(见第 4 阶段第 5 条)

## 人类伙伴发出的「你做错了」信号

**留意这些纠偏:**
- 「那个没发生吧?」——你未经核实就下了断言
- 「它会显示……吗?」——你本该先加证据收集
- 「别猜了」——你在不理解的情况下提修复
- 「往深处想」——质疑根本,不只是症状
- 「卡住了?」(不耐烦)——你的方法不奏效

**看到这些时:** STOP。回到第 1 阶段。

## 常见合理化借口(Common Rationalizations)

| 借口 | 现实 |
|--------|---------|
| 「问题简单,不用走流程」 | 简单问题也有根因。流程对简单 bug 很快。 |
| 「紧急情况,没时间走流程」 | 系统化调试比「猜了再试」的乱撞更快。 |
| 「先试这个,不行再调查」 | 第一次修复定下模式。一开始就做对。 |
| 「我先确认修复有效再补测试」 | 没测试的修复站不住。测试先行证明它。 |
| 「一次修多个省时间」 | 无法归因是哪个起的作用,还会引入新 bug。 |
| 「参考太长,我改编一下模式」 | 一知半解保证出 bug。完整读完。 |
| 「我看到问题了,直接修」 | 看到症状 ≠ 理解根因。 |
| 「再试一次修复」(失败 2+ 次之后) | 3+ 次失败 = 架构问题。质疑模式,别再修。 |

## 速查(Quick Reference)

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读错误、复现、查变更、收集证据 | 理解是什么和为什么 |
| **2. 模式** | 找能工作的例子、对照 | 识别差异 |
| **3. 假设** | 形成理论、最小化检验 | 假设被证实,或形成新假设 |
| **4. 实现** | 建测试、修复、验证 | bug 解决,测试通过 |

## 当流程得出「没有根因」

如果系统化调查揭示问题确实是环境性的、时序依赖的、或外部造成的:

1. 你已经完成了流程
2. 记录你调查过什么
3. 实施适当的处理(重试、超时、错误消息)
4. 加监控/日志,便于未来调查

**但是:** 95% 的「没有根因」其实是调查不完整。
